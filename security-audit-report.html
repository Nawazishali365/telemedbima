1Executive Summary

High-level overview of the audit scope, methodology, and headline findings.

The assessed application is a Node.js / Express frontend that proxies an upstream Spring Boot service (bcare.milvikpakistan.com) to drive a JazzCash "Direct To Consumer" (DTC) subscription flow for the BIMA MHealth product (Rs. 10/day or Rs. 300/month). The frontend is hosted behind Cloudflare and uses HTTPS with modern TLS.

However, the audit identified two CRITICAL vulnerabilities that completely bypass the proxy authentication model. Together, they allow any anonymous internet user to (a) obtain a valid 7-day service-account JWT, (b) query the subscription status of any Pakistani mobile number, and (c) request an HMAC-signed JazzCash "LinkWallet" payment payload — including the cleartext merchant password — for any phone number of their choosing. This constitutes end-to-end unauthenticated subscription-stuffing with direct financial impact on victims.

Scope
Two landing pages and three backend API endpoints (token, service-search, jazzcash-form). Upstream host bcare.milvikpakistan.com was checked for direct reachability.
Methodology
Passive review of served HTML/JS; active probing of exposed endpoints with no credentials; TLS/SSL inspection; security header analysis; common sensitive path enumeration.
Findings
13 issues total: 2 Critical, 4 High, 7 Medium, 4 Low. Plus 9 positive controls verified as working.
Tester Note
No payloads were submitted that completed a real payment. All testing used synthetic numbers (e.g. 03000000001) and inspected responses only.

3Critical Findings

Issues that must be remediated within 24 hours.

Critical

JazzCash merchant credentials leaked + arbitrary signed payment requests for any phone number

C1

Endpoint

GET /api/jazzcash-form?msisdn=<any>&transId=<any> — no authentication, no CSRF, no rate limit.

Evidence

The following response was returned for an attacker-supplied arbitrary MSISDN and transId, with no authentication required:

{
  "actionUrl": "https://onlinepayments.jazzcash.com.pk/payment-orchestrator/WalletLinkingPortal/wallet/LinkWallet",
  "pp_MerchantID": "8768948",
  "pp_Password": "p4hn4362xt",                              // ← plaintext merchant password
  "pp_RequestID": "attackerCanPickThis",                  // ← fully attacker-controlled
  "pp_ReturnURL": "https://bcare.milvikpakistan.com/jz/pk/callback/payment-token",
  "pp_MSISDN": "03007654321",                            // ← victim number attacker chose
  "pp_SecureHash": "18d9a7b50f3871ff68a3686c84cceb5c01b1da8a44abb390b25b4be354174bae"  // ← valid server HMAC
}

Why this is catastrophic

  • Cleartext pp_Password lets anyone impersonate BIMA's merchant identity against JazzCash. This credential must be considered fully compromised and rotated immediately.
  • For ANY MSISDN an attacker supplies, the server returns a valid HMAC-signed "LinkWallet" payload. An attacker can build a malicious page that auto-submits this form for any victim's phone number — the victim gets subscribed to Rs. 10/day charges without their consent or interaction. This is direct financial fraud.
  • Reproduced for multiple numbers (03007654321, 03331234567, 03000000001…). The transId parameter is fully attacker-controlled.
  • No throttling: 5 out of 5 rapid requests succeeded in ~250ms each. An attacker can mass-enumerate at will.

Remediation (do today)

  • Rotate the JazzCash merchant password AND the Integrity salt in the JazzCash merchant portal immediately. Treat both as compromised.
  • Stop returning pp_Password (and ideally pp_MerchantID) to the browser. The client does not need them — the server signs the payload and the browser just submits the form.
  • Bind the signed form to a server-side session that completed /api/service-search for that specific MSISDN, with a single-use CSRF token.
  • Reject caller-supplied transId. Always derive it from the prior service-search step stored server-side.
  • Add per-IP and per-MSISDN rate limits (e.g. 5/min) and a CAPTCHA threshold after 3 attempts from one IP.
  • Log and alert on every call to /api/jazzcash-form with the source IP.
Critical

Unauthenticated issuance of 7-day service-account JWTs

C2

Endpoint

POST /api/token — no body, no authentication, no rate limit.

Evidence

Every anonymous call returns a 7-day JWT bound to the same service user id:

// Decoded JWT payload (HS256):
{
  "iss": "Prashant",                                  // ← developer name as issuer = dev config in prod
  "iat": 1783052502,
  "exp": 1783657302,                                  // ← 7-day validity
  "sub": "{\"token\":\"501615c6...\",\"type\":\"auth-token\",\"userId\":2013864437756051456}"
}

Why this is critical

  • Every anonymous caller gets the same 7-day token bound to the same userId (2013864437756051456). All callers effectively operate as the same backend service account.
  • Combined with C1, an attacker can: → get a token → query any MSISDN's subscription status via /api/service-search/{msisdn} → generate a signed payment form for that MSISDN. End-to-end unauthenticated subscription-stuffing.
  • The JWT uses alg=HS256. If the secret is weak or default, tokens can be forged. Verify the secret is ≥32 random bytes and rotate.
  • No throttling: 3 out of 3 rapid requests succeeded in ~330ms each.

Remediation

  • Replace the shared service-account token with per-session tokens bound to MSISDN + device fingerprint.
  • Shorten TTL to 5–15 minutes; implement refresh semantics if longer sessions are needed.
  • Issue the token as an HttpOnly; Secure; SameSite=Strict cookie so JavaScript (and XSS) cannot read it.
  • Add per-IP rate limit (e.g. 5/hour) on /api/token.
  • Change iss from a personal name to a service identifier (e.g. bima-tp-frontend).
  • Rotate the JWT signing secret; verify ≥32 random bytes.

4High Findings

Significant exposure that materially weakens the security posture; should be fixed within days.

High

Upstream host bcare.milvikpakistan.com is directly internet-reachable

H1

Evidence

The JavaScript comments in the served HTML reveal the intended design: jzmhealth should proxy calls to bcare, but the upstream host accepts direct traffic:

// Served HTML comment:
POST to https://bcare.milvikpakistan.com/authorize/tp/login (proxied via /api/token)

// Direct probe of upstream:
$ curl https://bcare.milvikpakistan.com/
HTTP/1.1 301 Moved Permanently
Server: nginx/1.24.0 (Ubuntu)
Location: https://bcare.milvikpakistan.com/ui/

$ curl -X POST https://bcare.milvikpakistan.com/authorize/tp/login
{"status":415,"error":"Unsupported Media Type","path":"/authorize/tp/login"}  // Spring Boot responds directly

Impact

  • Attackers can bypass the proxy entirely and call the Spring Boot APIs on bcare directly — sidestepping any future rate-limit or WAF rules applied at jzmhealth.
  • Also leaks server software (nginx 1.24.0 (Ubuntu)) and the existence of a Spring Boot app.

Fix

  • Restrict bcare ingress to jzmhealth's origin IP / Cloudflare Worker egress only.
  • Block all direct external access at the firewall level.
High

Permissive CORS policy with credentials

H2

Evidence

// OPTIONS /api/token preflight response:
access-control-allow-methods: GET, POST, OPTIONS, PUT, PATCH, DELETE
access-control-allow-headers:  X-Requested-With, Content-Type, auth-token, x-api-key
access-control-allow-credentials: true

Impact

  • access-control-allow-credentials: true combined with no observed strict Origin allowlist means a malicious website could potentially call your API from a victim's browser using their cookies or token.
  • If any Origin is reflected back as Access-Control-Allow-Origin, the combination with credentials is a textbook CORS-bypass vulnerability.

Fix

  • Implement a strict Origin allowlist (only https://jzmhealth.milvikpakistan.com).
  • Never use * with credentials.
  • Reject all other Origins with a 403.
High

Weak / incomplete Content Security Policy

H3

Evidence

content-security-policy: frame-ancestors 'none';  // ← only this; nothing else

Impact

  • CSP contains only frame-ancestors. There is no script-src, no connect-src, no form-action.
  • Inline <script> blocks are unrestricted — every page contains large inline JS including the Firebase config and the form-submission logic.
  • Any XSS can exfiltrate the JWT from JS memory and POST phone numbers to attacker-controlled domains.

Fix

Adopt a strict CSP, e.g.:

default-src 'self';
script-src 'self' https://www.gstatic.com https://www.googletagmanager.com https://analytics.tiktok.com 'sha256-<inline-hash>';
connect-src 'self' https://bcare.milvikpakistan.com https://onlinepayments.jazzcash.com.pk https://www.google-analytics.com https://analytics.tiktok.com;
form-action https://onlinepayments.jazzcash.com.pk 'self';
frame-ancestors 'none';
base-uri 'self';
object-src 'none';
High

No rate limiting on any endpoint

H4

Evidence

Five rapid sequential requests to /api/jazzcash-form all returned 200 in ~250ms each:

Req 1: 200 (0.243077s)
Req 2: 200 (0.237790s)
Req 3: 200 (0.248389s)
Req 4: 200 (0.249943s)
Req 5: 200 (0.250050s)

Impact

  • Enables mass subscription-stuffing: an attacker can hammer /api/jazzcash-form for thousands of MSISDNs per minute.
  • Also enables token-issuance DoS against /api/token and abuse of /api/service-search for user-enumeration.

Fix

  • Add Cloudflare WAF rate-limit rules for /api/token, /api/service-search/*, and /api/jazzcash-form.
  • Add per-IP and per-MSISDN limits at the Express layer (e.g. express-rate-limit).
  • Implement exponential backoff and temporary IP bans for repeat offenders.

5Medium Findings

Defence-in-depth gaps and information disclosure that aid attackers or harm privacy.

IDIssueImpact & Fix
M1 /package.json exposed Returns 200 with project name (telemed-bima), entry point (server.js), and dependencies (dotenv, express). Reveals stack and likely config-file naming. Fix: Block /package.json, /package-lock.json, /server.js, /.env*, /node_modules/ at Cloudflare.
M2 No HSTS header HTTP→HTTPS 301 redirect exists but first HTTP visit is SSL-strip vulnerable. Fix: Enable HSTS in Cloudflare: Strict-Transport-Security: max-age=63072000; includeSubDomains; preload.
M3 Framework fingerprinting x-powered-by: Express header and the default Cannot GET /api/ error page both leak the framework. Fix: app.disable('x-powered-by'); replace default error handler with a generic JSON 404.
M4 PII mishandling (phone numbers) MSISDN travels as URL path param (/api/service-search/03001234567) — lands in Cloudflare logs, nginx logs, browser history, and could leak via Referer. Numbers also stored in localStorage (user_phone_e164, jazzcash_source) and sent raw to the TikTok pixel (ttq.identify({phone_number: e164_phone})). Fix: Move MSISDN to POST body. Use sessionStorage or omit storage. Send SHA-256 hashed identifiers to TikTok. Add a privacy disclosure.
M5 Deprecated X-XSS-Protection header X-XSS-Protection: 1; mode=block is deprecated by modern browsers and can introduce vulnerabilities in legacy engines. Fix: Remove; rely on a strong CSP instead.
M6 Upstream server version disclosure bcare returns Server: nginx/1.24.0 (Ubuntu) and verbose Spring Boot error JSON ({"timestamp":...,"path":...}). Fix: server_tokens off; in nginx; set server.error.include-message=never in Spring Boot.
M7 Implicit consent on BimaVoucher page There is no checkbox on the BimaVoucher page — "agreeing" simply means clicking Subscribe. This is weak both legally (under PDPB 2023 / consumer protection law) and from a UX-abuse perspective. Fix: Add an explicit unchecked checkbox that must be ticked to enable the Subscribe button; log the consent timestamp + T&C version server-side.
